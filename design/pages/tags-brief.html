How this was decided

Four independent proposals were produced from four stances - mobile-first, density-first, report-fidelity, minimal-change - each grounded in the real files: the token sheet, the existing previews, TimerPage.svelte, ReportsPage.svelte, PrintReportPage.svelte, report.ts. Each was then judged by three adversarial reviewers on distinct lenses: totals correctness and offline LWW, one-handed phone use, and consistency with the palette and the Time off colour semantics.

mobile-first 5.3 density-first 4.3 minimal-change 4.3 report-fidelity 4.0

Scores are low across the board - the judges rejected something in every proposal. The design below is the winner with the runners-up's strongest ideas grafted in and every fatal flaw fixed.

Data model, settled before anything visual

Tags are tags: string[] of lowercase names on the time_entries row itself. No tags table, no join table, no tag ids.

LWW resolves per row on updated_at, so a tag edit has to be one row write - identical to editing a description, offline-safe, zero new sync machinery. A fourth synced table would also break sequence allocation: sync.go:32 computes totalRows by hand over exactly three tables and derives nextSeq = lastSeq - totalRows + 1, so a table missing from that sum hands out sequence numbers outside the reserved block and clients silently miss rows on pull. Verified in the code, not assumed.

The cost, accepted: the tag list is one LWW unit, so two devices tagging the same entry concurrently resolve as last-writer-takes-the-whole-set rather than as a union. Identical to how description already behaves.

The decisions

  1. Colour. One neutral chip. No per-tag hue, ever - hue means project, and teal/purple/danger mean vacation/dayoff/sick. --accent is the selected state only. Absence is a shape: dashed and italic.
  2. Chips on rows. Yes, on a second meta line beside the project - one chip plus +N. Never in the description line.
  3. Grouping by tag. Split: an entry with k tags contributes billable/k to each. Always an untagged bucket, distinct from the user tag other.
  4. Creating tags. In the picker (normalised, case-insensitive match). Rename, merge and remove-from-all in Settings, behind count-bearing confirms.
  5. Print. No pills. A dim ·-separated trail after the description in Детализация, plus a По тегам figure with single-ink bars, без тега hatched and last. Suppressed entirely when nothing in range is tagged, so historical reports do not grow an empty section.
  6. Editor. Native <dialog> + showModal(): sheet below 34rem, 32rem card above. Not inline. A live boundary line replaces "seeing the neighbours".
  7. Running entry. Full editor; To empty with a running placeholder, typing a time stops it retroactively, Stop now as the shortcut. To can never be cleared.
  8. Time input. Free-text mono, 24h, accepts 930 and friends, arrow-key nudges, invalid disables Save. A +Nd stepper makes overnight entries representable.
  9. Delete. No confirm - immediate, with an 8s undo toast in the app shell. Tag removal in Settings keeps its confirm.
  10. Row layout. Flex, three parts: .dot, .main{flex:1 1 auto;min-width:0}, .when{flex:0 0 auto}, kebab. The description is a button that opens the editor.
  11. Sync hardening ships with it. updateEntry(id, patch) instead of whole-row writes, mergeServerRows skips rows still holding a dirty marker, pushes chunk at 2000 rows, and an HTTP 400 falls back to one row per request so a single bad row is quarantined instead of blocking the batch.

Why the totals still add up

One number per entry, one weight function, and the weights always sum to 1: 

tableTotal
  = Σ groups Σ entries in group  billable(entry) / k(entry)
  = Σ entries  billable(entry) × k(entry)/k(entry)
  = Σ entries  billable(entry)

So the header total does not depend on Group by - switching between Project, Tag, Day and Description never changes it. That property is new: the current overlaps-once code rounds group sums, so 15 project groups and 30 day groups produce different totals today. Fixed here for every grouping at once.

Two consequences that had to be stated in the UI rather than hidden. Rounding and overlaps-once become mutually exclusive, because rounding a deliberately halved share re-inflates the overlap the option exists to remove - exportCSV already passes overlapOnce ? 0 : rounding for exactly this reason, and the UI is being brought in line with the export. And the Entries column is a count, not a total: an entry with two tags is one entry in each of two groups, so group counts sum above the distinct count while durations do not.

Risks accepted, not solved

A 60-minute meeting tagged meeting + review reports as 30m under each - a number the user never entered. It is the price of reconciliation and it bites 358 of 10 835 real entries. The 1/k marker and the table caption are the only mitigation.

No tag colours means a tag-heavy day is scanned by reading, not by pattern, and there is no escape hatch - the palette is genuinely exhausted, so granting tag colours means reopening decision 1.

Undo is an 8-second window. Closing the PWA loses the affordance; no "recently deleted" list ships.

Rename and merge move updated_at on every affected row, so a merge touching thousands of entries clobbers concurrent edits from another device that have not yet been pulled.

The +Nd stepper makes overnight entries possible but nobody will look for it; an entry typed 23:40 to 00:20 gets its offset bumped with no signal beyond the duration readout.
