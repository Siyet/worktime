# Бэкенд: Go vs Bun

Контекст проекта: opensource self-hosted аналог solidtime/clockify. ~10 пользователей, multi-user с Google OAuth (без ролей и команд). Несколько одновременных таймеров. MCP-сервер. Требования: минимум ресурсов на сервере, простой self-hosting.

БД в обоих вариантах - SQLite (WAL-режим): при 10 пользователях и характере нагрузки time-tracker'а (редкие короткие записи) вывозит с запасом на порядки. Ноль отдельных процессов, бэкап = копия файла.

Итог: выбран **Go** (решение от 2026-07-24).

---

## Что такое Hono и Elysia

Веб-фреймворки для JS-рантаймов - то же место в стеке, что FastAPI/Litestar в Python или chi/echo в Go.

### Hono

Минималистичный роутер + middleware + валидация:

- ~14KB, ноль зависимостей, работает на Bun/Node/Deno/Cloudflare Workers.
- Киллер-фича - Hono RPC: бэк экспортирует ТИП роутера, фронт создаёт клиент и получает полный автокомплит по всем эндпоинтам, параметрам и ответам. Без кодогенерации: поменял эндпоинт на бэке - tsc на фронте сразу красный.

```ts
// backend: routes.ts
const app = new Hono()
  .get("/api/entries", (c) => c.json(listEntries()))
  .post("/api/entries", zValidator("json", entrySchema), (c) => ...);
export type AppType = typeof app;

// frontend: api.ts
import type { AppType } from "@worktime/server";
const client = hc<AppType>("/");
const res = await client.api.entries.$get(); // типизировано насквозь
```

### Elysia

Bun-first фреймворк, по духу ближе к Litestar:

- Schema-first через TypeBox, e2e типизация через Eden (аналог Hono RPC).
- Быстрее Hono на Bun в бенчмарках, богаче из коробки (Swagger, guards, плагины).
- Минусы: жёстко завязан на Bun, тяжёлая магия типов - ошибки компиляции бывают нечитаемые.

Если брать Bun - рекомендация Hono: проще, переносимее, понятнее ошибки.

## Вариант A: Go (выбран)

Стек: Go 1.25+, chi (роутер), modernc.org/sqlite (pure-Go драйвер, без CGO), golang.org/x/oauth2 (Google OIDC), modelcontextprotocol/go-sdk (официальный MCP SDK), go:embed (статика фронта внутри бинарника).

### Ресурсы

- RAM: 15-30MB idle.
- Docker-образ от scratch: 15-20MB. Можно вообще без Docker - один бинарник + systemd.
- Холодный старт мгновенный.

### Разработка

- SQL: sqlc генерит типизированный Go-код из сырых SQL-запросов - опечатки и несоответствия типов ловятся на этапе генерации, не в рантайме.
- Контракт с фронтом: OpenAPI-спека -> openapi-typescript. Шаг кодогенерации (одна команда, вешается в CI и pre-commit). Типы обновляются автоматически, но это не "нативный" шаринг.
- Claude пишет Go отлично, системных ловушек нет.

### Self-hosting

Для opensource-продукта один бинарник - сильный аргумент: "скачал, запустил, открыл localhost:8080". Ни docker-compose, ни рантаймов, ни внешних зависимостей. У solidtime для сравнения - PHP + Laravel + очереди + Redis, поднимать заметно тяжелее.

### Минусы

- Два языка в проекте, переключение контекста.
- Типы фронт/бэк синхронизируются кодогеном, а не компилятором TS.
- Больше однотипного кода на CRUD, чем в TS.

## Вариант B: Bun (отклонён)

Стек: Bun 1.2+, Hono, bun:sqlite (встроенный нативный драйвер), @modelcontextprotocol/sdk (TypeScript, референсная реализация MCP), arctic (OAuth).

### Ресурсы

- RAM: 60-120MB (движок JavaScriptCore).
- Docker: oven/bun slim ~80-100MB. bun build --compile даёт standalone-бинарник, но ~90MB.

### Разработка

- Один язык на весь проект. Монорепа: apps/server, apps/web, packages/shared (доменные типы).
- E2E типы через Hono RPC - главный ускоритель соло-разработки: рефакторинг API мгновенно подсвечивает все сломанные места на фронте, без шага кодогенерации.
- bun:sqlite синхронный - для запросов на миллисекунды при 10 юзерах не проблема, зато нет overhead пула соединений.
- MCP TypeScript SDK - самый зрелый из всех, фичи протокола появляются в нём первыми.

### Минусы

- RAM в 3-5 раз больше Go. В абсолюте немного, но требование "минимум ресурсов" выполняется хуже.
- Bun моложе: изредка ловятся баги рантайма (с каждым годом меньше).
- Standalone-бинарник тяжёлый (~90MB), self-hosting story менее красивая.

## Сводная таблица

| Критерий | Go | Bun + Hono |
|---|---|---|
| RAM idle | 15-30MB | 60-120MB |
| Docker-образ | 15-20MB | 80-100MB |
| Деплой без Docker | один бинарник ~15MB | бинарник ~90MB или рантайм |
| Типы фронт <-> бэк | кодоген из OpenAPI | нативно через TS (Hono RPC) |
| MCP SDK | официальный (Go) | официальный, референсный (TS) |
| Google OAuth | x/oauth2, тривиально | arctic, тривиально |
| Скорость соло-разработки | средняя | высокая (один язык, e2e типы) |
| Зрелость рантайма | эталон | хорошая, но моложе |
| Качество Claude-кода | отлично | отлично |

## Вердикт

Оба вывозят 10 пользователей с запасом на порядки. Выбор - trade-off:

- **Go**: минимум ресурсов + лучший self-hosting story для opensource-продукта.
- **Bun**: скорость итераций + один язык на весь проект + e2e типы без кодогенерации.

Выбран **Go**: требование минимума ресурсов жёсткое, а кодоген типов - решённая проблема (одна команда в CI). Бонус - привлекательность для self-hosters как продукта.
